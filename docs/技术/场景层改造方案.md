# 先做场景层的依据（与裁决层的关系）

> 结论：**先做场景层**。裁决层再聪明，上游只给 41% 的时间有素材，它也只能空转。

---

## 一、依赖方向

```
感知层 ──┐
         ├─→ 裁决层 ─→ 生成层
场景层 ──┘
```

裁决层读两边的数据：

| 来源 | 裁决用它做什么 | 现状 |
|---|---|---|
感知 | 意图/情绪/连续度 → 硬约束 | 够用（246 条真实数据，判断稳定） |
场景 | 有没有可讲的事 → 决定 advance | **只有 41% 的时间有素材** |

所以：感知层可以先不动，场景层是瓶颈。

---

## 二、数据：场景层现在给了多少

用场景池 + 生命周期模拟（20 天 × 5 分钟粒度）：

| 方案 | 有可讲素材的时间占比 |
|---|---|
现状（pending 只活 30 分钟） | **41.2%** |
只做生命周期（pending→doing→done） | **69.2%** |
生命周期 + 每个场景都配一件具体事 | **100%** |

再叠加意图分布（246 条真实感知）：

```
分享 68 · 敷衍 37 · 试探 79 · 提问 50 · 倾诉 8 · 求建议 4
可走"场景开关"的（分享/敷衍）= 42.7%
```

**裁决层里场景规则的实际触发率**：

```
现状：41.2% × 42.7% ≈ 18%
改造后：100% × 42.7% ≈ 43%
```

也就是说：**现在六轮里只有一轮能用上场景**，改完接近一半的轮次都有素材。

---

## 三、场景层 v2 要改成什么

### 3.1 数据结构（向后兼容，只加字段）

```js
{
  location: '家',
  doing: '在厨房煮面',
  since: 1793...,
  minutes: 12,

  // 新增：带生命周期的事项
  items: [
    { text: '锅里的水快开了', phase: 'doing', at: 1793..., doneAt: null }
  ],

  // 新增：刚做完的事（保留 2 小时）
  done: [
    { text: '衣服晾完了', at: 1793... }
  ],

  // 新增：给裁决/生成用的种子（按优先级排好）
  seeds: ['锅里的水快开了', '衣服晾完了']
}
```

保留 `pending: [{text, at}]` 字段（旧的 UI、proactive 仍在读），由 `items` 派生出来，**不改调用方**。

### 3.2 生命周期

```
0-25 分钟     phase = 'pending'    → seeds 第一条
25-45 分钟    phase = 'doing'      → "正在做"
45 分钟以后   phase = 'done'       → 进 done 列表，保留 2 小时
```

`done` 的用途：她可以说"刚把衣服晾了""面吃完了"——这是最像真人的一类开场。

### 3.3 补全场景池

现在 40 条里有 10 条没有 pending（发呆/躺着/刷手机这类）。

补成"一件具体的小事"：

```
家 / 在发呆            → 待办：袜子配不成对
床上 / 刷手机           → 待办：明早闹钟又没设
路上 / 在走过去          → 待办：鞋里进了颗小石子
```

补完覆盖率到 100%。

### 3.4 给裁决的显式契约

```js
hasSeed: scene.seeds.length > 0      // 有没有话可说
seed: scene.seeds[0]                 // 说哪件事
pace: 'quiet' | 'normal' | 'busy'    // 由 location 决定
```

`pace` 的来源（地点语义表）：

```
地铁 / 路上 / 通勤   → busy   回复短，别长篇
公司 / 咖啡店        → normal
家 / 床上 / 沙发     → quiet  可以长一点、软一点
```

### 3.5 事件表（可选，第二阶段）

```sql
CREATE TABLE scene_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  qq TEXT NOT NULL,
  text TEXT NOT NULL,
  at INTEGER NOT NULL
);
```

用途：主动消息可以说"今天我跑了三趟楼下"，而不是每次只看当前场景。

## 四、影响面（改之前必须知道）

| 消费方 | 现在读什么 | 改动后 |
|---|---|---|
`brain.mjs` sceneBlock | location/doing/pending | 追加 seeds |
`proactive.mjs` | `scene.pending[0]` | 改用 `scene.seeds[0]` |
`index.mjs` findConflict | location | 不变 |
Web UI（Memory/Sandbox/Turns） | location/doing/pending | **字段保留**，不用改 |
DB state 里的旧 JSON | 无 items/done/seeds | 读取时补默认值，兼容 |

**关键：只加字段、不删字段**，所以 UI 和旧数据都不用迁移。

---

## 五、验证方式

```
1  单元测试（时间旅行）：把 now 打进 0/20/40/70 分钟，断言 phase 与 seeds 正确
2  模拟：已跑，覆盖率 41.2% → 69.2% → 100%（scripts/scene-coverage-sim.mjs）
3  影子日志：记录每轮"advance 用到的素材来源"（pending/done/doing）
   目标：pending+done > 70%
4  线上观察 1 天：主动消息里"具体事件类"占比是否上升
```

## 六、顺序与工时

| 步骤 | 做什么 | 工时 |
|---|---|---|
1 | 场景 v2：items/done/seeds + 生命周期 + 补全 10 条场景 | 0.5 天 |
2 | 消费方改读 seeds（proactive / brain） | 0.2 天 |
3 | 单测 + 模拟回归 | 0.2 天 |
4 | 裁决 v3（规则 + 场景开关 + strength） | 0.5 天 |
5 | 影子 1 天 → sandbox 1 天 → 生产 | 观察期 |

**总计 1.5 天开发 + 2 天观察。**

---

## 七、风险

| 风险 | 应对 |
|---|---|
旧场景 JSON 没有新字段 | 读取时 `?? []` 兜底 |
`pending` 与 `items` 双写不一致 | `pending` 由 `items` 派生，不单独维护 |
补全场景后话题更碎 | seeds 取优先级最高的一条，不死板 |
done 保留 2 小时导致"刚做完"过时 | done 超过 2 小时自动丢弃 |

## 八、一句话

```
场景层决定"她有没有话可说"，裁决层决定"这轮该不该说"。
先让上游一直有话说，下游的规则才有意义。
```
