# 裁决层改造方案 · v2（含验证结果）

> 结论先说：**不要做全量打分**。实测打分版对权重极度敏感，一个权重从 0.8 调到 1.2，advance 占比能从 0% 跳到 38%。
> 改用 **"规则表 + 场景开关 + strength"**，确定性可解释，验证通过。

---

## 一、现状问题（读代码所得）

`src/act.mjs` 的 `decideAct` 只有 63 行、5 个分支：

```
提问/求建议 → answer    倾诉 → engage    敷衍 → advance
话题耗尽 → deflect      连续度低 → deflect  难过/焦虑 → engage
默认 → answer
```

| # | 缺陷 | 证据 |
|---|---|---|
| 1 | 拿不到 `scene` | 入参只有 `perception/recentActs/mood` |
| 2 | 拿不到 `goal` | `replyGoal()` 只进 prompt，没进裁决 |
| 3 | 没有强度 | 撒娇 0.7 和 0.95 同处理 |
| 4 | act 集中 | 线上 246 条真实感知：**answer 80.9%**，sticky 0% |

> 附：`ask-media` **不是死分支**——它由看图路径 `mediaAct()`（media.mjs:155）触发，只是不在 `decideAct` 里。

## 二、验证过程（用线上 246 条真实感知回放）

数据：`perceptions` 表 261 行，可用 246 条（2 个用户），来自生产。

### 实验 1：全量打分版（v2）

候选 5 个 act 累加特征分（意图/情绪/连续度/场景/重复惩罚），分差算 strength。

| 指标 | 旧 | v2 打分 |
|---|---|---|
| answer | 80.9% | 59.3% |
| engage | 3.7% | 10.6% |
| advance | 14.2% | 11.8% |
| deflect | 1.2% | 0.8% |
| sticky | 0% | 17.5% |
| 分布熵 | 0.90 | 1.65 |
| 判断改变 | — | 72 条（29%） |

**问题暴露**：

```
· 60% 的改变 strength < 0.3，是随机抖动在决定，不是真信号
· 重复惩罚把 answer 扣掉后，「他在提问」被判成 sticky —— 打分和正确性打架
```

### 实验 2：改成两层（硬约束 + 打分）

| 指标 | 旧 | 两层版 |
|---|---|---|
| answer | 80.9% | 84.1% |
| 判断改变 | — | 14 条（6%） |

结果几乎等于旧版——因为回放数据里**没有 scene 和 goal**，打分版的优势发挥不出来。

### 实验 3：场景权重敏感性（关键发现）

同一批感知，只改"有 pending 时 advance 的加分"：

| pending 加分 | advance 占比 |
|---|---|
| 不加场景 | 15.0% |
| **0.8** | **15.0%**（完全没影响） |
| **1.2** | **53.3%**（过冲 38 个百分点） |

**结论：线性加权在这套输入上是刀锋状态，0.8 和 1.2 相差 38 个百分点，不可控。**

### 实验 4：规则 + 场景开关（v3，推荐）

设计：

```
① 硬约束（正确性优先）
   提问/求建议 → answer
   倾诉/难过/焦虑 → engage
② 场景开关（新增）
   有 pending 且他在分享/敷衍 → advance
③ 话题耗尽 → deflect（不连岔）
④ 接不上（continuity<0.2 且 certainty≥0.6 且上轮没岔）→ deflect
⑤ 他敷衍且她刚说完自己的 → sticky
⑥ 默认 answer
```

同一批数据回放：

| 场景 | answer | engage | advance | deflect |
|---|---|---|---|---|
| 无场景 | 90.2% | 3.7% | 0% | 6.1% |
| 有 pending | 53.3% | 3.7% | **42.7%** | 0.4% |

**确定性、可解释、无刀锋**：pending 开关一开，advance 从 0 变 42.7%，且每条都能说出理由。

> 42.7% 是因为实验里给**所有**样本都挂了 pending；线上 pending 大约一半时间存在，实际 advance 约 20%，合理。

## 三、最终方案（v3）

### 3.1 接口

```js
decideAct({
  perception,   // 已有
  recentActs,   // 已有
  mood,         // 已有
  scene,        // 新增
  goal,         // 新增（安抚/接话/给建议…）
  meta,         // 新增 { hasImage, textLen, hour }
})  // → { act, why, strength }
```

### 3.2 strength 怎么定（不再靠分差）

```
硬约束命中（他在问 / 他在倾诉）   → 0.9（坚决执行）
场景开关命中                     → 0.7（有话说，但不是非说不可）
话题耗尽 / 接不上                → 0.5-0.6
默认接住                         → 0.5
```

下游用法：

```
strength ≥ 0.7 → prompt 里写得坚决（"这轮就这么说"）
strength ≤ 0.4 → 写成"可带过"，允许模型自然接
```

### 3.3 可配置

`ACT_WEIGHTS` 改名为 `ACT_RULES`：

```js
{
  pendingAdvance: true,        // 有 pending 时是否允许 advance
  pendingNeedsShare: true,     // 仅在分享/敷衍时触发
  deflectBelow: 0.2,
  deflectMinConf: 0.6,
  moodLowEngagePenalty: true,
}
```

## 四、上线方式（灰度 + 影子）

```
ACT_V2=0  默认关，旧逻辑
ACT_V2=1  新规则生效
ACT_SHADOW=1  只记录不生效（日志写"旧=X 新=Y"）
```

顺序：

```
1  本地 246 条回放（已完成，本文数据）
2  线上影子 1 天，人工抽 30 条看是否更合理
3  sandbox 开 1 天，看对话是否变跳
4  生产开
```

回滚：改一行环境变量。
